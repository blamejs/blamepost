Self-hosted mail

One process serves every protocol your mail needs.

blamepost runs inbound MX, authenticated submission, IMAP, JMAP, POP3, ManageSieve, outbound delivery, DKIM signing, Sieve filtering, webmail and an operator console from a single Node process against a single data directory. It has no npm runtime dependencies and no build step.

Every listener, one boot sequence

Each listener is one framework primitive composed into the same process. All are on by default except POP3.

IMAP and POP3 negotiate TLS in band, so this server binds 143 and 110 and binds nothing on 993 or 995. JMAP mounts inside the web application at /jmap rather than on a port of its own, so it inherits the same session and security middleware as the rest of the HTTP surface.

What it looks like

The browser surface is server-rendered. Client JavaScript is opt-in, and the theme switch works with scripting off.

What it does

Submission is identity bound

SASL AUTH binds the authenticated account to the envelope sender. A MAIL FROM the account does not own is refused at the wire, and the finished message's From is checked against the same set. Active aliases and subaddresses count as sending identities.

Mail leaves signed, twice

Every outbound message carries an Ed25519 signature (RFC 8463) and an RSA-SHA256 one (RFC 6376), so a receiver that cannot verify the first falls back to the second. Signing keys are sealed on the data volume. Minting, rotation with overlap, and retirement are console and CLI verbs.

One outbound path, policy composed

MX lookup, MTA-STS enforcement (RFC 8461), DANE (RFC 7672), REQUIRETLS when you ask for it (RFC 8689), retry with backoff, and delivery status notifications (RFC 3464). Mail this server sends on its own behalf takes the same path, and a repository gate refuses a raw transport call.

Arriving mail is authenticated

SPF, DKIM verification, DMARC and ARC are evaluated at the end of DATA and written into Authentication-Results, after any header claiming this server's name is stripped. SPF, DKIM and DMARC reach the disposition.

Reports you can act on

Aggregate DMARC reports are ingested, parsed and counted per domain: volume, alignment, the senders failing both checks, and who reported. The console says whether the evidence carries the next policy step, and publishes the _dmarc record against a diff you confirm.

Deletion has one path

IMAP EXPUNGE, POP3 DELE, JMAP Email/set and the browser all arrive at the same agent, which enforces per-message legal hold and an optional one year retention floor before anything leaves the volume.

Credentials for applications

A sending credential is scoped to one hosted domain, holds a rolling ceiling on messages and on recipients, refuses postmaster and abuse by default, and gets its own return path so bounces reach a mailbox you named. Present it on 587 or 465, or post JSON to /api/send with an idempotency key.

Post-quantum where the choice is ours

ML-KEM-1024 for key agreement, ML-DSA-65 for release signatures, XChaCha20-Poly1305 for sealing, SHAKE256 and SHA3-512 for digests, HKDF-SHA3-512 for derivation, and Argon2id for passwords. Stored mail, credentials and signing keys are sealed with those primitives.

Everything is written down

Administrative actions write hash-chained audit rows carrying what changed, when, how it came out and who did it, with hourly signed checkpoints. A command line invocation records the operating-system account; a console action records the signed-in one.

What it does not do yet

This is pre-1.0 software and the list matters as much as the one above. The roadmap in the repository marks every capability as shipped, targeted, accepted or under design.

  • It does not obtain or renew certificates. Point it at a certificate and key on disk from whatever already issues yours. A renewal written to those paths is picked up without a restart.
  • It does not filter spam. No blocklist lookup, greylisting or content scoring is wired into the delivery path.
  • It does not create, rename or delete folders in the browser. An IMAP client does all three. The default set is made at first use.
  • Sieve rules are not editable in the browser. Scripts are uploaded, listed, activated and deleted over ManageSieve. redirect and vacation are refused wherever they appear.
  • Webmail compose offers no attachment control, and does not save drafts. A forward still carries the message it forwards.
  • It binds nothing on 993 or 995. A client that can only do implicit TLS to a mailbox has no route here today.
  • It reads no TLS-RPT reports. It sends them; parsing what comes back is not in this release.
  • There is no post-quantum DKIM, here or anywhere. The signature registry has no ML-DSA value, so such a signature would be unverifiable by every receiver.
  • It relays for nobody. Give the printer or the application server an account, or a sending credential.

Run your own

The server is a plain Node process. Nothing is transpiled, so the source in the repository is the code the runtime executes. 

git clone https://github.com/blamejs/blamepost.git
cd blamepost
bash scripts/vendor-update.sh blamejs latest

export BLAMEPOST_HOSTNAME=mx.example.com
export BLAMEPOST_VAULT_PASSPHRASE='a long random string you keep offline'

node bin/blamepost.js init  --data-dir ./data --admin-email admin@example.com
node bin/blamepost.js serve --data-dir ./data

The vendor step is required on a fresh clone. Before the first message you publish an MX record, an SPF policy ending in -all, a DMARC policy at p=quarantine or stricter, a DKIM selector record per domain, an MTA-STS policy and a TLS-RPT endpoint. The MX listener refuses to bind until you confirm that posture, and blamepost doctor resolves the records and reports what is missing. The container image and the day-2 operations are covered in the operator guide in the repository.
