Give a mailbox its attempts back

An address this server hosts no mailbox at is refused rather than reported released, so a typo here cannot read as a fix.

A smaller budget is kept against each source address on its own. Leaving this empty releases the mailbox and leaves that one alone, which is what refuses the account holder from one machine while every other machine works. Copy it out of the table above rather than retyping it: a machine this server cannot read as an address refuses the whole release, mailbox included, rather than releasing half of it under a notice that reads as a fix.

Required, and recorded in the audit trail against you. Releasing a budget is the one action here that takes a defense away from somebody else's mailbox.

Reading the counts

A count of wrong passwords is an early warning and nothing else. The failure that spends a budget resets the count, because the wait that follows is the answer rather than the number, so a budget that is holding somebody out reads zero and so does a mailbox nobody has ever guessed at. That is why no count is shown beside a budget that is holding. What is worth reading there is the Times column in the table above: how many times that budget has run out, which is what sets how long each wait is.

The Recorded column is what was written down when a budget ran out, and Right now is the counter itself. They answer different questions and they can disagree. The counters are held in this running process and the rows are on disk, so a lockout recorded before a restart stands over a budget that is already free, and the row says so where that has happened.

What this releases, and what it does not

Five wrong passwords inside a quarter of an hour spend a mailbox's budget. The wait that follows starts at a minute and grows with each further run at the same mailbox, up to six hours, and the count decays a quarter of an hour after the last failure. A source address the mailbox has already signed in from is still let in while the budget is spent, which is why a desk machine often keeps working while a phone does not.

Each listener that authenticates also counts authentication failures per source address, and that budget is a separate one. Nothing on this page releases it, nothing on this page reads it, and nothing in this server can do either. It does not work the way the mailbox budget above does: it is a rolling quarter of an hour, so it lifts a quarter of an hour after the earliest of the failures that spent it, not after the most recent attempt. Once the budget is spent the listener refuses the sign-in and closes the connection before it reaches the password, so nothing further is counted and going on trying does not push the wait back. A mailbox that reads clear here can still be refused on one protocol, from one machine, until that window passes.

The sign-in form itself has a third bound, and it counts something different again: not wrong passwords but posts, whatever they carried, {{ signInPosts }} of them in any {{ signInMinutes }}-minute slot from one source address. Past that the form answers Too Many Requests until the slot ends. It is a ceiling on work rather than on guessing, because every post to that form costs this server one password check whether or not the address named has a mailbox here. Nothing on this page reads or releases it, and waiting out the slot is the only thing that clears it.

The source address it counts against is the machine this server sees on the connection, and that is not always the reader's. Behind a terminator holding the certificate for the web interface, every browser arrives from the terminator's own address and that count is shared across everyone signing in. It is well clear of a busy morning and nowhere near a script, so the bound still separates the two; if you reach it, everyone waits out the same slot.

This is not the way to stop an account signing in. A spent budget is a mailbox that cannot get in and should be able to; suspending it on the accounts page is a mailbox that should not, and the two are separate gates.
