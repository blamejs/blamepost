# Roadmap

blamepost is a self-hosted mail server: SMTP, IMAP, JMAP, POP3, ManageSieve and a browser interface in one container, built post-quantum-first with no npm runtime dependencies and security defaults wired into the boot sequence rather than exposed as flags. It composes the vendored blamejs framework, which owns the wire protocols, the mail-store substrate and the cryptography, and adds the parts a framework deliberately leaves to an application: identity and addressing, message composition and sending, the browser interface, and the operational surface an operator runs the thing through.

This document tracks capability areas and the standards they target, in rough delivery order. Every item is marked **Shipped** (available in the current release), **Targeted** (committed for a near-term release), **Accepted** (agreed as in scope, scheduled later), or **Under design** (shape still being settled). Status changes as capabilities ship; [CHANGELOG.md](CHANGELOG.md) is the record of what is released today.

A note on the current state, so this document is read correctly. The server exists and runs. Every listener in the table below binds, mail arrives over SMTP and is readable over IMAP, JMAP and POP3, Sieve runs at delivery, the browser interface and the operator command line are both there, and the release and supply-chain pipeline is in place. Mail also leaves: a message handed to the delivery composer reaches a peer's socket with its body unaltered, and a recipient that fails permanently ends with a delivery report addressed to whoever sent it. What is unfinished from here is breadth rather than a path that does not run, and the label on each item below is what says which.

Two labels are easy to misread, so they are worth spelling out. *Substrate shipped* means the framework primitive exists and is verified, which says nothing about whether blamepost composes it: read the sentence after the label for that. And an item stays **Targeted** while its surface is incomplete against the standard it names, even when the working parts of it are running today, because 1.0 is a promise about standards completeness rather than about a feature being reachable. An honest backlog is more useful than a flattering one, in both directions.

## What 1.0 means

1.0 is the point where an operator can put blamepost in front of a domain and stop reading release notes for breaking changes. Concretely: every shipped listener is standards-complete for the verbs it advertises and interoperates with the clients people actually use; the on-disk format is stable, with a migration path across any change to it; the public surface carries the upgrade guarantee of deprecation warnings at least one minor before removal and no silent breaks in a minor, that surface being the CLI, the configuration schema, and the IMAP and JMAP behavior an operator's clients depend on; and the support window in [LTS-CALENDAR.md](LTS-CALENDAR.md) takes effect. Pre-1.0 none of that is promised, and the version number says so.

## Foundations

The decisions everything else rides on. This is the part that exists today.

- **Vendored framework, sourced from the registry.** *Shipped.* `scripts/vendor-update.sh` is the single entry point for changing `lib/vendor/`. It resolves a version from the npm registry, verifies the publisher's `dist.integrity` digest before anything is extracted, extracts the tarball, records version, integrity and resolved URL in `lib/vendor/MANIFEST.json`, re-hashes the tree, and loads the vendored entry point in a fresh process so a tree that cannot be required fails here rather than at first boot. It fails closed when the digest mismatches or when no integrity value is published. `--check` is a CI drift gate that reports an unreachable registry as unknown rather than as current, because a network failure that reads as up to date is the one answer the gate must never give. Vendoring the published tarball rather than a git clone means the vendored tree is the artifact operators consume and carries only the package's file allowlist.
- **Zero npm runtime dependencies.** *Shipped.* The application resolves nothing from a registry at run time or at image-build time. The framework is vendored in-tree; `devDependencies` exist for the lint and coverage gates and never enter the container image.
- **Release trust roots.** *Shipped.* Four independently verifiable roots, each checkable without trusting the others: SSH-signed commits and tags, SLSA L3 provenance, Sigstore-keyless SBOM signatures, and byte digests over SHA-256 and SHA3-512 alongside an ML-DSA-65 sidecar signature. The public key the fourth verifies against ships in the repository at `keys/release-pqc-pub.json`; the workflow's sidecar step skips with a warning until the `RELEASE_PQC_SIGNING_KEY` secret is set in the publish environment, and the other three ship either way. The verification recipes are in [SECURITY.md](SECURITY.md).
- **Supply-chain gates.** *Shipped.* Actions and container base images are digest-pinned with currency checks; secret scanning, dependency review, static analysis and workflow linting run per pull request; the vendored pin is measured against the registry on every run so a dependency that stopped moving blocks a release rather than going unnoticed for a year.
- **Container image definition.** *Shipped.* A two-stage build that runs as an unprivileged user, drops every capability, adds only the application tree and the one shared library the runtime base omits, and declares a single data volume. Nothing the image is configured to run goes through a shell: the entry point, the default command and the health probe are all argument arrays. The base itself supplies busybox and the Node package tooling, which the image's own package inventory lists, so an operator sizing what a code execution defect would reach sizes it against that rather than against an empty filesystem. The image carries no operating system package manager, which is the half of that posture an operator can rely on: no apk, apt, dnf or yum, so nothing inside can fetch a toolchain from the network. The integration suite pins the whole set, so a base image that grows a package manager or loses an interpreter the record names is reviewed rather than inherited. The privileged-port question is settled explicitly rather than by running as root: a container's own network namespace already starts the unprivileged-port floor at zero on current runtimes, so the image binds the mail ports as an unprivileged user with every capability dropped and no sysctl set, and the documented default sets the sysctl anyway to state the requirement for a runtime that has not adopted the floor. Under host networking that floor is the host's own and the sysctl is refused rather than applied, which is the case every listener port being overridable answers.
- **Configuration model.** *Targeted.* A single schema validated at boot, with an environment layer over an optional file, and a fail-loud posture on a value the server cannot honor. Configuration errors surface at start rather than at the first message.
- **Process and lifecycle.** *Targeted.* One process serving every enabled listener, with ordered startup, readiness that reports listener state rather than mere liveness, and signal-driven draining that closes listeners, finishes in-flight sessions and flushes the queue within a bounded deadline.

## Inbound mail (RFC 5321)

- **MX listener.** *Targeted. Substrate shipped.* `b.mail.server.mx` implements the RFC 5321 state machine with SMTP-smuggling defense at the wire layer, a required TLS context with no implicit plaintext mode, per-peer rate limiting on by default, and an optional relay grant for peers inside an operator-named address range. blamepost composes it with local-domain resolution, a per-address check at RCPT and the delivery path, and passes no relay grant, for the reasons under the entry below. RFC 5321.
- **Relay for a source address.** *Shipped as a refusal.* The MX listener relays for nobody, and `BLAMEPOST_RELAY_ALLOWED_FOR` stops the boot rather than being ignored. The setting stays declared rather than being deleted, so an operator who had one reads a sentence saying why it is refused and naming which origin supplied the value, instead of finding that the variable had quietly stopped meaning anything. An empty list asks for nothing and starts normally. The reasoning is what makes this a position rather than an omission. Every listener here requires STARTTLS before it will accept an envelope, on port 25 as much as on submission, so a device that can reach `RCPT TO` has already completed a handshake it could have authenticated over. The only device an address range could serve that an account cannot is one that speaks no TLS at all, and that device never gets past the greeting either way. A range also names a segment rather than a party, so withdrawing one compromised host means withdrawing every device behind it, where `blamepost account suspend` withdraws one. Relayed mail could not be signed here in any case, because signing it would let anything on that segment emit mail aligned under a hosted domain's key, which is the forgery the author binding exists to refuse. A device that genuinely cannot hold a credential wants a submission relay of the operator's own in front of it, which keeps that credential in one place rather than extending trust to a whole segment.
- **Command and envelope shape enforcement.** *Targeted. Substrate shipped.* `b.guardSmtpCommand` validates per-verb command shape and detects body smuggling; `b.guardEmail` and `b.guardMessageId` validate addresses and message identifiers. Wire-protocol readers refuse malformed input with the protocol's defined error code rather than tolerating it for compatibility, which is the discipline the parser vulnerability history in this space argues for.
- **Bounded MIME parsing at accept.** *Targeted. Substrate shipped.* `b.safeMime.parse` parses with hard depth and size bounds so a crafted structure is rejected in bounded time.
- **Internationalized addresses.** *Accepted.* SMTPUTF8 acceptance, with `b.mail.toAscii` and `b.mail.toUnicode` for the conversion boundary. The MX listener defaults to refusing non-ASCII command bytes, so this is a deliberate opt-in rather than a default. RFC 6531.
- **Delivery into the store.** *Shipped.* Accepted messages append through the mail-store substrate, which parses, threads, seals and quota-accounts at append. The recipient's active Sieve script runs first and decides which folder the message lands in.

## Message submission (RFC 6409, RFC 8314)

- **Submission listener.** *Targeted. Substrate shipped.* `b.mail.server.submission` implements RFC 6409 submission on 587 and RFC 8314 implicit TLS on 465, offering SASL over PLAIN, LOGIN, SCRAM-SHA-256, EXTERNAL and XOAUTH2, and refusing `MAIL FROM` until authentication succeeds. blamepost composes both ports and advertises `PLAIN` alone, because the other four each need state this server does not keep: a reproducible shared secret for the challenge-response mechanisms, a client certificate identity for EXTERNAL, and a token issuer for XOAUTH2. Widening that set is the work this item is about, and SCRAM is the one worth having first.
- **Identity-bound envelope sender.** *Shipped.* The authenticated account is bound to the envelope sender, and a `MAIL FROM` for an address the account does not own is refused at the wire with `553 5.7.1 Sender address rejected: not owned by authenticated identity`, before any recipient is accepted. This is a hard rule rather than a policy option, and the session survives the refusal so a client that guesses wrong once can correct itself.
- **Identity-bound author.** *Shipped.* The envelope is only half of an identity. `MAIL FROM` is the address a receiver bounces to and never shows anybody; `From` is the address a person reads, and binding the first alone left an authenticated account able to display any address at any hosted domain, signed with that domain's key and arriving DMARC-aligned. The submission relay measures the finished message before anything signs or sends it: every address in `From` or `Sender` at a domain this server hosts has to be one the account may write, and at least one address across the two has to be, so the message is attributable to somebody who signed in for it. A message carrying no `From`, a second `From` or `Sender`, an RFC 6854 group naming nobody, or a header block that cannot be read is refused whatever it names. Delegation for an outside author is not refused: `From: partner@example.net` under `Sender: alice@example.com` is accepted, because this server's key creates no alignment for a domain it does not host and that domain's own policy is what answers for the message. The refusal is permanent on the wire and says which half failed: an author the account may not write draws `550 5.7.1`, and a `From` and `Sender` pair that names no single readable author draws `550 5.6.0`. The reply itself is short; the rejected address and the set that would have been accepted are in the log and in an audit row. RFC 5322 §3.6.
- **A refusal that chooses its own reply.** *Shipped.* A rejection at the agent handoff names the reply it wants rather than inheriting one, through `smtpCode`, `enhancedStatus` and `replyText`, each checked on its own: a code outside 4yz and 5yz is not honored, an enhanced status whose class contradicts the code is replaced with the code's class, and the text is injection-checked like every other operator string on the wire. Permanent decisions carry their own reply. Submission refuses an author the account may not write at `550 5.7.1` and a header block that names no single readable author at `550 5.6.0`, and both SMTP listeners refuse a body carrying an end-of-data sequence RFC 5321 §4.1.1.4 does not define at `554 5.7.0`. The delivery handoff answers by what refused the message: an address this server does not deliver to at `550`, a message the parser will not read at `554`, whether the reason is its structure, its headers or a transfer encoding or character set this server does not read, and a message over a size ceiling at `552`. Everything else answers `451 4.3.0`, and so does a message refused for more than one reason at once, because a single reply covers every recipient on it. A full mailbox, a suspended account, a disabled domain and a full outbound spool are conditions their owner or the operator clears, so the peer keeps the message and retries on its own schedule. RFC 5321 §4.2.1.2, §4.2.2, RFC 3463.
- **Sending under an alias.** *Shipped.* An active alias that lands in an account's mailbox is an address that account may speak for, in `From` and in `MAIL FROM` alike, so `sales@example.com` aimed at `alice@example.com` is an address alice sends under from an ordinary mail client as well as from the browser and JMAP. Both halves measure one set, resolved from the store on every envelope rather than fixed when the session authenticated, so an alias the operator withdraws stops being a sending identity at the next message rather than at the next sign in. For an address at a domain this server hosts, both halves answer from that one set, so neither permits what the other refuses. They part company on an author somewhere else: `From: partner@othercorp.example` under a `Sender` this account may write is accepted, because this server's key creates no alignment for a domain it does not host and that domain's own policy answers for the message, while the same address in `MAIL FROM` is refused, because the envelope is the return path and has to name a mailbox here. Two addresses reach a mailbox without joining that set. A catch-all is not an identity, because it claims every name at a domain and counting one would hand the account holding it every address the domain could ever carry. Neither is an address arriving through a second alias: the set follows one alias row while routing follows a chain, so such an address is delivered and is still not one the account may write. An alias in a second hosted domain is an identity too, and a message sent under it is signed for that domain on every surface: the browser and JMAP sign for the domain in the `From` header they build, and a client that puts the alias in the envelope as well is signed for it from there.
- **Sending from your own subaddress.** *Shipped.* An RFC 5233 tag folds against the same canonical form routing folds it against, in `From` and on the envelope, so `alice+receipts@example.com` is an address alice writes in both and the port that sends and the port that receives give one answer about one address. A mail client configured with a subaddress as its identity puts that address in `MAIL FROM` and in `From` and sends. The fold reads the mailbox an address is delivered to rather than dropping the part it cannot check, so a tag on somebody else's local part is still refused `553 5.7.1`: `bob+receipts@example.com` is bob's address carrying a tag, not alice's. The failure budget kept against a mailbox folds the tag away for the same reason, so a tag cannot refill it.
- **Domain-scoped sending credentials.** *Targeted. The submission transport is shipped; the ceilings do not survive a restart and no console surface issues one.* An application that has to send as a hosted domain without holding one of its mailboxes presents a credential rather than an account password. `blamepost credential add` issues one against a hosted domain, and it may write any local part at that domain in `From` and on the envelope, signed with that domain's key and arriving DMARC-aligned. The scope comes off the row on the volume rather than out of the token, under a keyed digest computed with a key the vault passphrase seals, and the domain the client names at sign-in has to be the domain the row names, so a token pasted into an application for another domain fails at the sign-in. Each message is measured on the envelope sender and on the `From` and `Sender` header through the one decision an account is measured through, so the two halves of the wire binding cannot disagree about an address. Only the submission listener holds that identity space: IMAP, POP3 and ManageSieve read a credential as no identity and refuse it the way they refuse a wrong password, so a secret issued to send mail opens no mailbox in the domain it speaks for. The second transport is `POST /api/send`, which takes the credential as a bearer token, refuses a request that also carries a browser cookie, and reaches the same envelope check, the same author binding, the same ceilings and the same relay handle the port reaches. Three things keep this Targeted. The two ceilings each credential carries, one on messages and one on recipients over a rolling window, are counted in the running process alone, so a restart returns every credential its full window and an operator who needs a ceiling that survives one has none. The verbs that change a credential open the data volume and a running server holds it, so issuing or withdrawing one means stopping mail; the administration console is where they belong and does not carry them yet. And nothing narrows a credential below the whole domain, so an application that only ever writes one address holds a credential that can write every address in it.
- **Credential handling.** *Targeted. Substrate shipped.* `b.auth.password` provides Argon2id hashing, rehash detection and a policy check that includes a bundled breach-derived common-password set. The failure budget `b.auth.lockout` provides is composed and described under anti-abuse below. RFC 9106.
- **Per-account submission limits.** *Accepted.* Rate and volume budgets per account, so one compromised credential cannot burn the server's sending reputation before anyone notices.
- **8-bit mail.** *Shipped.* RFC 6152 lets a body carry 8-bit content and senders using a legacy character set still produce it, so the two places that could quietly alter such a message both work in octets. The signer hashes and returns the bytes that were sent rather than a decoded copy, which is one guarantee in two halves: hashing a decoded copy emits a signature that fails at every receiver, and returning one emits a signature over a message the sender never wrote. The mailbox protocols read it back the same way, so `RETR`, `TOP`, `FETCH BODY[]` and a partial fetch all return the stored octets and count the window in octets, which is what RFC 9051 §6.4.5 counts in. What still leaves a message unsigned has nothing to do with its character set: a domain this server holds no active selector for cannot be signed for, and that is recorded under an action of its own so it can be alerted on separately from a key that will not unseal.

## Message authentication

- **SPF.** *Targeted. Substrate shipped.* `b.mail.spf` verifies and parses records. The operator-side posture documented for hosted domains is strict, with `-all` rather than a soft fail. RFC 7208.
- **DKIM verification and signing.** *Targeted. Substrate shipped.* `b.mail.dkim` verifies inbound signatures with a per-message signature cap and clock-skew bounds, and signs outbound. RFC 6376, RFC 8463 for Ed25519.
- **Dual signing.** *Targeted. Substrate shipped.* `b.mail.dkim.dualSigner` signs every outbound message twice, once with Ed25519 and once with RSA-SHA256, so a receiver that has not implemented RFC 8463 still gets an authenticated message. Both selectors ship, and neither is optional. RFC 8463 §3, RFC 6376.
- **Per-domain signing algorithm.** *Accepted.* Both selectors sign every message and the pair cannot be split today: no setting turns one algorithm off, and `blamepost dkim retire` names a pair and takes both halves, so withdrawing a selector by hand takes its partner with it rather than leaving the domain signing with the other. RFC 6376 §6.1 already requires a verifier to evaluate the signatures it understands and to keep going past the ones it does not, so a receiver that mishandles the second header is the thing that is wrong; the operator whose mail it is still pays for it, which is what makes this worth building rather than only worth arguing about. What it needs is a mode recorded on the domain rather than a selector taken away: which algorithms sign, honored where the signer is built, reported by `blamepost dkim` and `blamepost doctor`, refused where it would leave a domain with nothing to sign with, and recorded when it changes. A domain holding one algorithm because a mint stopped part way is the state that shows why the selector-withdrawal shortcut is not the same feature, since the only way out of it is to retire the remainder and mint a fresh pair, with the domain unsigned in between. RFC 6376 §6.1, RFC 8463 §3.
- **Post-quantum DKIM.** *Under design, blocked externally.* Not offered, and not a matter of implementation effort. The `DKIM-Signature` `a=` tag draws from an IANA registry that has no ML-DSA value, so a post-quantum signature would be unverifiable by every receiver rather than merely unsupported by some. The blocking work is standardization, not code. When a key type is registered, adopting it adds a third selector alongside the existing pair rather than replacing either, and the vendored framework's ML-DSA-65 primitive is already the piece that would sign it.
- **DMARC evaluation and reporting.** *Targeted. Substrate shipped.* `b.mail.dmarc` evaluates alignment and parses records, and both parses and builds aggregate reports and parses failure reports. Organizational-domain derivation runs through `b.publicSuffix`. The revised specification splits the subject across three documents, which supersede the original RFC 7489: RFC 9989 for the protocol, RFC 9990 for aggregate reporting, RFC 9991 for failure reporting. Auditing the vendored implementation against the revision, in particular the tree-walk that replaces the public-suffix organizational-domain lookup, is tracked as its own item.
- **DMARC revision audit.** *Targeted.* The vendored implementation predates the revised specification. Auditing it against RFC 9989, RFC 9990 and RFC 9991 covers the organizational-domain tree walk that replaces the public-suffix lookup, the policy-discovery changes, and the reporting-format changes, with anything the framework needs going to blamejs rather than into a patch on the vendored tree.
- **ARC.** *Targeted. Verification composed, sealing not.* `b.mail.arc` signs, verifies and evaluates the chain a forwarder or a mailing list leaves behind to carry an authentication verdict across the hop that rewrote the message. The gate blamepost arms at DATA evaluates that chain and reports what it found as an `arc=` result in `Authentication-Results`: `none` for a message carrying no chain, `pass` for one that validates, `fail` otherwise. RFC 8617 §5.2 gives the chain only those three tokens, so `fail` covers a seal that was checked and did not hold and a sealer's key that could not be looked up alike; the structured verdict separates them and the `mail.server.mx.envelope_verdict` audit row carries the distinction, which is what stops a resolver outage reading as a forgery. What the result does not do is move the message, and that is a decision rather than an unfinished half. The verdict reaches this server's own delivery handoff beside the SPF, DKIM and DMARC results, so acting on it needs no further plumbing. What it needs is the setting that does not exist. A chain is worth exactly what its sealer is worth, and there is no setting here that names the sealers an operator vouches for, so anyone who can register a domain and publish a selector can seal a flawless chain over their own forgery asserting that a victim's domain passed. Until an operator can say which sealers they trust, a chain that validates cannot lift a DMARC failure and a broken one cannot cause a refusal. The trust that can be expressed today is narrower and more honest: a recipient's own Sieve script reads the `arc=` result and files on it, and the account holder who subscribed to the mailing list is the person who actually knows they trust it. What keeps this item Targeted is the other direction. Nothing on the way out adds a seal, so a message this server forwards reaches the next hop with no chain recording what authenticated here. RFC 8617.
- **Authentication-Results.** *Targeted. Substrate shipped and composed.* `b.mail.authResults.emit` records the verdict in the header receivers and clients read, and the gate blamepost arms at DATA writes it on every accepted message. RFC 8601.
- **Reverse DNS and HELO discipline.** *Targeted. Substrate shipped.* `b.mail.iprev`, `b.mail.reverseDns` and `b.mail.helo` cover forward-confirmed reverse DNS and generic-rDNS heuristics. blamepost composes `b.mail.helo` against the single resolver handle every lookup on this server shares rather than against the host's stub, so the HELO check and the SPF, DKIM, DMARC and ARC checks read one view of the zone. Which upstream that handle asks is not an operator setting yet, which is a second thing keeping this item Targeted. What it does not do is check its own reverse DNS: `blamepost doctor` resolves the zone's mail records and no `PTR`, so the one posture failure that costs the most deliverability is the one an operator still has to check by hand.
- **BIMI.** *Accepted. Substrate shipped.* `b.mail.bimi` parses records, fetches policy, validates the constrained SVG profile and verifies the mark certificate against the verified-mark and common-mark policy identifiers. Display of an indicator is a client concern; what blamepost owns is publishing and verification. IETF draft.

## Mailbox access: IMAP (RFC 9051)

- **IMAP4rev2 listener.** *Targeted. Substrate shipped.* `b.mail.server.imap` implements RFC 9051 over STARTTLS, with `b.guardImapCommand` enforcing per-verb shape, literal framing and literal-injection refusal, and per-peer rate limiting. This server composes the STARTTLS mode on 143 and no implicit-TLS one; the entry below covers that.
- **Implicit TLS on the mailbox listeners.** *Targeted. Substrate shipped, not composed.* RFC 8314 §3 asks for implicit TLS on 993 and 995 in preference to the in-band upgrade, and `b.mail.server.imap.create`, `.pop3.create` and `.managesieve.create` each take `implicitTls: true`, wrapping the accepted socket from the first byte, declining to advertise or accept the upgrade verb, and defaulting the port to 993 or 995 where the RFC names one. This server binds 143 and 110 and composes neither. Turning it on is a listener rather than a flag: it needs a port and a listener section in the configuration schema, a row in the firewall table and the operator guide's port table, entries in the container's exposed ports and the compose file's published ones, and a wire vector per protocol proving the greeting opens inside TLS and the upgrade verb is gone. A TLS terminator is not a substitute and never was: behind one the listener is handed a plaintext connection and refuses every credential, which is the correct answer to a hop asking to be believed about confidentiality it terminated. RFC 8314.
- **Change synchronization.** *Targeted. Substrate shipped.* The store maintains a per-folder modification sequence, and the IMAP listener serves CONDSTORE over it, so a client resynchronizes a large mailbox by sequence rather than by refetching. QRESYNC is not advertised. Serving it needs a `VANISHED` response for every UID expunged since a client's mod-sequence, on `SELECT`, on `EXPUNGE` and on `FETCH`, which needs a record of expunged UIDs the mailbox layer does not keep, and a `FETCH` composition that writes `VANISHED`. RFC 7162.
- **Mailbox annotations.** *Shipped.* The listener advertises `METADATA` and `METADATA-SERVER` and answers `GETMETADATA` and `SETMETADATA` for the account's own mailboxes. RFC 5464.
- **Removing, renaming and subscribing to a mailbox.** *Shipped.* `CREATE`, `DELETE`, `RENAME`, `SUBSCRIBE` and `UNSUBSCRIBE` all answer, and `LIST` reads its reference, its patterns and its `SUBSCRIBED`, `CHILDREN` and `STATUS` options. `DELETE` destroys the mail the mailbox holds through the one delete path, so a message a preservation order or the retention window keeps stops the removal: the client is answered `NO [CONTACTADMIN]` with the count that was kept, and the mailbox is still there holding it. `INBOX` and the five mailboxes carrying an RFC 6154 role are refused, because this server files into those by name. A removed mailbox that still has names underneath it stays in a listing as `\NonExistent \HasChildren`, so what is under it is still reachable. `RENAME` moves the inferior names with the name above them, creates the superior levels the new name needs, and keeps the mailbox's `UIDVALIDITY`; renaming `INBOX` moves the messages into a new mailbox and leaves `INBOX` in place, empty. `DELETE` and account erasure remove the message store's folder behind each mailbox they remove, so a client that creates and deletes mailboxes in a loop leaves the store's folder list the size it was. A subscribed name outlives the mailbox it names, which `UNSUBSCRIBE` is the only thing that removes. `LIST`'s `RECURSIVEMATCH` selection option is refused by name: serving it means the `CHILDINFO` data item for every match. RFC 9051 §6.3.5, §6.3.6, §6.3.7, §6.3.8, §6.3.9.
- **Draining a refused non-synchronizing literal.** *Shipped.* `LITERAL+` (RFC 7888) is not advertised on IMAP and the command guard refuses a `{N+}` announcement. The octets of a non-synchronizing literal are already on the wire when that refusal is written, so the IMAP and ManageSieve listeners do not read them as commands. Where the listener knows the count, as for a ManageSieve `PUTSCRIPT` before authentication or an `AUTHENTICATE` naming a mechanism it does not offer, it discards that many octets and answers one refusal. Where the wire guard refuses the announcement itself, the listener answers the refusal, then `BYE`, and closes the connection. A synchronizing `{N}` literal is refused before its payload is sent, and the connection stays open.
- **Copying and moving between mailboxes over IMAP.** *Under design.* `COPY` and `MOVE` are answered `NO`, and so is `UID EXPUNGE`. A message moves between an account's mailboxes over JMAP and in the browser interface today, through the one path that keeps the message store's row and this server's row in step; `COPY` and `MOVE` need the same path plus the `COPYUID` and `MOVE` responses RFC 9051 §6.4.7 and §6.4.8 define. `UID EXPUNGE` (RFC 9051 §6.4.9) removes the subset of `\Deleted` messages a UID set names, which is a second set of arguments reaching the delete path rather than a spelling of `EXPUNGE`, so serving it means the retention floor and the legal hold are asked of that set.
- **Stable cross-protocol identity.** *Targeted. Substrate shipped.* Every message carries an object identifier, so the same message is addressable as an IMAP UID and a JMAP id without a mapping table that can drift. RFC 8474.
- **Quota.** *Targeted. Substrate shipped.* Per-account and per-folder byte and message counters are maintained atomically with append and delete. RFC 9208.
- **Client interoperability.** *Accepted.* Validation against the clients people actually use rather than only against this project's tests. An implementation this project did not write should exercise every protocol it speaks.

## Mailbox access: JMAP (RFC 8620, RFC 8621)

- **JMAP Core and Mail.** *Targeted. Substrate shipped.* `b.mail.server.jmap` is HTTP-mounted rather than a separate listener, so it rides the web application's request lifecycle and authentication. It is served at `/jmap` inside the web application, not on a port of its own.
- **Push.** *Targeted.* Two of the three channels RFC 8620 section 7 describes are served, and a client finds both in the session document rather than by convention. The event source stream is a route on the web application. The WebSocket transport is attached to the upgrade event on the same ports: it negotiates the `jmap` subprotocol RFC 8887 requires, carries method calls through the dispatcher the API endpoint already uses, requires the same signed in account, and refuses an origin this server does not serve. Either one tells a mailbox owner that their own mail changed without a poll, and neither carries anything about another account. What is not there is the third channel, the web push subscription of RFC 8030: there is no `PushSubscription/set`, so a client that wants to be woken while it is disconnected has nothing to subscribe with. Two bounds are worth knowing before relying on this. A change is found by reading the account's modification sequence about once a second rather than being raised by the code that wrote it, so the notification trails the write by up to that long. And a `StateChange` names `Mailbox` and `Email` and never `EmailDelivery`, because the sequence advances on a flag change as readily as on an arrival, and telling a client mail arrived when none did is worse than telling it neither. RFC 8620 section 7, RFC 8887.
- **Blob download.** *Shipped.* A client fills in the `downloadUrl` the session document names and fetches one blob over the account session it already holds. The template carries the four RFC 8620 section 6.2 variables, and two of them decide the answer: the accountId is refused unless it is the one the signed-in account is enumerated for, and the blobId names what is served. A blob id is a message identifier, which answers that message's raw octets and is the value `Email.blobId` carries, or that identifier followed by `-p` and the part number RFC 9051 section 6.4.5 gives the part, with each dot written as a dash because RFC 8620 section 1.2 admits no dot in an Id. Resolution runs under the signed-in account, so a blob id another account holds answers the same refusal as one nothing holds, and the parts a blob id reaches are the parts the browser interface lists for the same message. Every blob is served as `application/octet-stream` with `nosniff`, whatever the sender declared and whatever the client asked for, and is disposed as an attachment under the name the message carries, written in both RFC 6266 section 4.1 forms. The name in the URL is the client's own suggestion and is not served.

  `Email/get` names those blob ids in `attachments`, so a client takes one out of the answer rather than building it from the grammar above. The property is answered only to a call that names it in `properties`: listing the parts opens the message and walks its structure, and one call may name fifty identifiers. Measured over fifty messages each carrying a 256 KiB file, naming it adds about 300 ms and reads 12.5 MiB; over fifty messages that carry none it adds nothing, because the mark written when each was filed already records that there is nothing to list.

  Each part carries `partId`, `blobId`, `size`, `name`, `type`, `charset`, `disposition`, `cid`, `language` and `location`, which is the default body-property set of RFC 8621 section 4.1.4. `headers` and `subParts` are absent: every part in the list is a leaf, and the header list belongs with the `header:*` forms of section 4.1.3 rather than on its own. `bodyProperties` is not read, so a client naming it is answered the whole set. A message above the octet read bound carries no `attachments` at all rather than an empty one, which is the same third answer `hasAttachment` gives it.

- **Message bodies over JMAP.** *Accepted.* `attachments` is the only body-part property `Email/get` answers, so `bodyStructure`, `textBody`, `htmlBody` and the `bodyValues` of RFC 8621 section 4.1.4 are absent and a client reads a message's text through `preview` or by downloading the whole message under its `blobId`. The three arguments that fetch body values, and the `bodyProperties` projection over each part, belong in the same change.

- **Blob upload.** *Accepted.* The upload endpoint answers 503 and the session document advertises `maxSizeUpload` as 0, so a client reads the limit before it tries. Two pieces are missing, and both are storage questions. Octets that belong to no message yet need somewhere account-scoped and bounded to live, with a reclaim path for the ones a client uploads and never refers to. And `Email/set` needs to create a message from them, which it does not do today.

## Mailbox access: POP3 (RFC 1939)

- **POP3 listener.** *Targeted. Substrate shipped.* `b.mail.server.pop3` covers the RFC 1939 state machine with capabilities, STLS and SASL, and blamepost composes it against the same mailbox adapter, permission table and expunge path the other listeners reach. It is off by default and exists for clients that cannot speak IMAP or JMAP, so an operator who wants it sets `BLAMEPOST_POP3_ENABLED=true` and the listener binds 110. A client that sends `AUTHENTICATE PLAIN` with no initial response is answered here exactly as it is on IMAP and submission, which is the entry below. What keeps this Targeted is what keeps every listener here Targeted: it has been exercised against this project's own tests rather than against the clients people actually use, which is the item under Client interoperability above. RFC 1939, RFC 2449, RFC 2595, RFC 5034.
- **Multi-line SASL on every listener.** *Shipped.* Submission, IMAP, POP3 and ManageSieve all carry an authentication exchange that spans more than one line, so `AUTHENTICATE PLAIN` with no initial response is answered with a challenge and the client's next line completes it. One verifier serves all four, so a client is answered the same way whichever port it arrived on and a rule about credentials cannot hold on one listener and not the one beside it. Each writes the challenge in its own syntax: the IMAP continuation, the SMTP `334` reply, the POP3 `+` line, and on ManageSieve a zero-length literal, which RFC 5804 §2.1 is what makes an empty ask expressible there at all. Only the opening step may challenge, because a second one is an exchange with no end. The round trip is an ordinary one and costs no part of the account's authentication-failure budget, and a client that withdraws with a single `*` is answered as having withdrawn rather than as having guessed wrong. RFC 4954 §4, RFC 9051 §6.2.2, RFC 5034 §4, RFC 5804 §2.1.

## Filtering (RFC 5228, RFC 5804)

- **Sieve evaluation at delivery.** *Shipped.* The recipient's active script runs against every message that arrives for them, inbound from a peer and from a local sender alike, and `fileinto`, `keep` and `discard` are dispatched. The script reads the message's headers, its size in octets, and the envelope the peer declared, where `envelope :to` is the recipient written in `RCPT TO` rather than the mailbox behind it, so a rule can file on the alias a message arrived at. A script is checked before it is stored, which RFC 5804 requires of a server that accepts one, and the check covers both halves of what makes a filter run: the grammar, and whether the interpreter carries every action and test the script names. A script naming one it does not carry is refused at upload rather than refusing every message afterwards.

  A script that goes wrong never costs the message. A parse error is refused at upload, which is the only moment the account holder is there to be told. A script that survives upload and is still wrong at delivery, by naming a folder the account does not have or asking for an action this build cannot perform, delivers to INBOX and says so in the log. `discard` is the one case where a message reaches no folder, and it happens only because the owner wrote it down.

- **A bound on what one filter may spend per message.** *Targeted.* `b.mail.sieve` runs a script under a gas budget of ten thousand operations, and the budget counts operations rather than the work inside one of them. A `header :matches` naming a list of header names against a list of patterns performs the product of the two lengths as a single operation, and each of those comparisons walks the pattern against the header value, so the cost of one counted operation is the product of three lengths the budget never reads. Measured on this server's own caps: a 63 KiB script, accepted at upload and spending 28 of its ten thousand units, held the delivery thread for 57.8 seconds against a message carrying sixty 2,000-character `Received` headers. The delivery path is synchronous and the process serves every listener, so that time is the whole server. What bounds it today is the 64 KiB script ceiling, the 32-script ceiling, the message-size ceiling and the per-address connection and rate ceilings on the MX listener, and none of those is the quantity that actually grows. Charging the budget per comparison and per character walked is the fix, and it belongs to the interpreter rather than to a ceiling composed around it; this item closes when the interpreter's budget reads the work.
- **Sieve actions that need to send.** *Accepted.* `redirect` and `vacation` both put a message on the wire, and neither is performed yet. They are refused at different points, because the interpreter carries one and not the other. A script using `redirect` is stored and runs: at delivery the message is kept and the refusal recorded, so the account holder still gets their mail and the operator can see what was asked for and not done. A script using `vacation` is refused at upload, because the interpreter would refuse it on every message and take the rest of the script with it. The outbound path both of them need is in place, so what is left belongs to the actions themselves. `redirect` re-sends somebody else's mail from this server, which wants the envelope rewriting under Sender rewriting below so SPF survives the hop, and a bound on how far a chain of redirects may run. `vacation` needs the suppression state RFC 5230 requires, so that a responder cannot answer a mailing list or reply to the same sender twice in a week. RFC 5228 §4.2, RFC 5230.
- **Filing into a folder that does not exist.** *Under design.* RFC 5228 §4.1 lets a server either create the folder or deliver to INBOX. blamepost delivers to INBOX. IMAP `CREATE` now makes one, so the account holder can make the folder their script files into before the script runs, and the rule a name has to pass is the same one on both paths. What is still undecided is whether a delivery may make a folder on its own: a name arriving from a filter script is a name nobody has read, and a script that mistypes one would file mail into a mailbox its author never meant to make.
- **ManageSieve.** *Targeted. Substrate shipped.* `b.mail.server.managesieve` lets a client upload, list, activate, fetch, rename and delete scripts. RFC 5804.
- **Script management verbs.** *Targeted.* `sieve.activate` and `sieve.list` are among the agent methods the framework deliberately leaves unimplemented, so blamepost implements them over the store and exposes them through ManageSieve and the browser interface.
- **Vacation responses.** *Accepted.* `vacation.set` is likewise an application concern. Correct suppression behavior matters more than the feature: a vacation responder that replies to a mailing list or to a bounce is a deliverability incident. RFC 5230.
- **Rule editing in the browser.** *Accepted.* Most people will never write Sieve by hand. A structured editor that emits Sieve, with the source visible and editable for anyone who wants it.

## Outbound delivery and transport security

- **One delivery composer.** *Targeted. Substrate shipped.* `b.mail.send.deliver` performs MX resolution, MTA-STS enforcement, retry classification and DSN generation as one policy-composed path, and the retry schedule that classification feeds is kept beside it here. Every outbound path in the application goes through it, including the reports this server sends on its own behalf. A raw transport call from application code is a defect the pattern detector rejects, because a bypass is how a message escapes the transport-security policy the operator configured. All three transport-security policies that path is meant to carry now reach a peer: MTA-STS, DANE, and REQUIRETLS.
- **Refusing an unknown mailbox at RCPT.** *Shipped.* A peer offering an address this server does not host is refused `550 5.1.1` while it is still on the socket, which costs the sender nothing and tells them immediately. The listener's per-address hook is answered from the same resolution the delivery handoff uses, so the listener cannot accept an address the handoff would then have to refuse, and a refusal spends the per-peer recipient-failure budget, so the difference between `250` and `550` is not a free mailbox-enumeration channel. What the hook deliberately does not refuse is worth keeping in view before anything here changes. Only a permanent condition ends on the wire. A mailbox that is full, an account that is suspended and a domain that has been switched off are all accepted at RCPT and met at delivery instead, because the owner can clear every one of them, and telling a sender to stop retrying a condition that is about to clear is how mail gets lost with everybody satisfied. A store that cannot answer is not a verdict about the mailbox either, so that failure travels out and the peer is deferred rather than being told that a live mailbox does not exist. RFC 5321 §3.3.
- **Putting a message on the wire.** *Shipped.* The delivery composer reaches the framework's SMTP transport, the transport opens the socket, and what arrives at the peer is the message that was submitted rather than a copy rebuilt from structured fields: the bytes handed in are the bytes written after `DATA`, a body that is not valid UTF-8 included. Whether a build can send at all is measured rather than remembered, by asking the framework surface for the transport the composer will reach for at the first send, so `blamepost doctor` answers that question at boot instead of leaving an operator to infer it from a queue that stopped draining. A recipient a peer defers goes to the spool and spends the retry budget the ordinary way; one refused permanently ends with a delivery report to whoever sent the message.
- **MTA-STS.** *Targeted.* The web surface serves the policy body at `/.well-known/mta-sts.txt`, so an operator points `mta-sts.<domain>` at this process rather than standing up a second web server for one text file, and `BLAMEPOST_MTA_STS_MODE`, `BLAMEPOST_MTA_STS_MX` and `BLAMEPOST_MTA_STS_MAX_AGE` are what it reads. Outbound, the delivery composer enforces the policy, and the record that decides whether a domain publishes one at all is looked up here first over the resolver the operator pinned rather than over whatever the composer would otherwise ask. That distinction is the whole protection: RFC 8461 §3.1 makes one TXT record the gate on the policy, so a suppressed answer and an honest absence look alike, and a sender reading them alike delivers in the clear to a domain that asked for TLS. A domain whose record could not be settled is withheld from rather than delivered to, while one that publishes nothing is unaffected, which is what keeps mail moving to most of the internet. The documented posture is enforce rather than testing. What keeps this Targeted is that one policy body serves every hosted domain, so an operator hosting domains behind different mail exchangers cannot yet publish a policy per domain. RFC 8461.
- **DANE.** *Targeted.* DANE is meaningful only under a signed zone, which the operator guide says rather than presenting it as a free win. Outbound validation works: the composer carries the operator's statement about their resolver into the TLSA lookup, fetches the records for each mail exchanger it tries, and hands them to the transport, which matches the peer's certificate chain against them during the handshake. RFC 7672 §2.1.1 and §2.2 forbid using a record that was not DNSSEC-validated and nothing here can tell whether the resolver this server was given validates, since that is a fact about the resolver rather than about the server, so `outboundPolicy.dnssecValidated: true` is the operator's statement to make and `outboundPolicy.dane: "enforce"` without it is refused at boot rather than authenticating peers against records anybody on the path could have rewritten under a banner saying they were verified. Enforcing costs nothing at receivers who publish nothing: a host with no TLSA record answers empty rather than refusing, so only a lookup that genuinely failed takes an exchanger out. `"opportunistic"` stays the shipped default. What keeps this Targeted is the publishing half: the TLSA records an operator has to put in their own zone are not generated for them here, and `blamepost doctor --dane` checks that at least one covers the SMTP port rather than that it matches the certificate this server presents. RFC 7672.
- **REQUIRETLS.** *Shipped, off by default.* `BLAMEPOST_REQUIRE_TLS` puts the REQUIRETLS keyword on the `MAIL FROM` line of every peer whose post-STARTTLS EHLO advertises the extension, and a peer that does not advertise it is not delivered to: the message fails over to the next MX host for the recipient's domain, and is permanently failed with `5.7.30` once every host has been asked. RFC 8689 §4.1 requires that rather than a fall back to sending in the clear, and it is the whole value of the setting, because a sender told the message went cannot otherwise tell an encrypted delivery from one the receiver never promised to encrypt. The default is off for the same reason: most receivers do not implement the extension, so a server that asks every peer for it stops delivering to most of them. Turn it on where you know your correspondents support it. A host skipped before the send, a DANE lookup failing mid-rollover, never answered the question, so a run containing one stays deferrable rather than bouncing. RFC 8689.
- **Sending TLS-RPT reports.** *Shipped.* Every delivery to a domain that publishes `_smtp._tls` leaves a record of how transport security went with it, and once a day that record becomes an RFC 8460 aggregate report addressed where that domain asked for it. Where to send is resolved at the moment of the report over this server's own resolver rather than read from anything cached at send time, because a forged `_smtp._tls` answer redirects this server's own failure reports. Both destination forms RFC 8460 §3 allows are served: an `https://` destination is posted to directly, and a `mailto:` one is composed as mail and takes the same outbound path, policy chain, spool and retry budget as everything else. A domain publishing no record is sent nothing and its counts are dropped, since nobody asked for them; a domain whose record could not be resolved keeps its counts for the next day, since a resolver that was briefly unreachable is not a receiver waiving a report; a published destination that refused the report keeps them too. What a report carries is bounded on purpose. Only the RFC 8460 §4.3 result types are ever reported, so a delivery that failed on a full mailbox or an exchanger that would not resolve is counted as nothing rather than as a receiver's broken TLS, which would be a signed accusation about something else entirely. One thing is worth knowing before reading a report as evidence: the counts it covers leave the accumulator once it reaches the outbound path rather than once it arrives, so a report that fails after that point takes that day's observations with it. RFC 8460.
- **Reading TLS-RPT reports.** *Targeted. Substrate shipped.* `b.mail.deploy` parses aggregate reports and offers an HTTPS ingestion endpoint, the HTTPS form having a smaller abuse surface than the mail form. Neither half is mounted here yet, so an operator's `rua=` has to name a destination they run or a mailbox on this server that they open themselves, and the operator guide says so rather than implying otherwise. RFC 8460.
- **Sender rewriting.** *Accepted. Substrate shipped.* `b.mail.srs` rewrites the envelope sender on forwarding so SPF survives the hop.
- **Queue.** *Targeted.* A durable spool on the data volume, one descriptor and one message body per waiting recipient, swept by a timer that retries whatever is due. Each descriptor carries its own attempt count and its own record of what has been tried on it, so a rising backoff runs per recipient and a receiver that is transiently broken forever becomes a permanent failure with a report rather than a file that lives forever. An entry leaves the spool only once an attempt has finished, so a message is never off disk and un-sent at the same time. The backoff is a rising schedule per recipient rather than per receiving domain, so a hundred messages bound for one struggling receiver each keep their own clock instead of sharing its. That is what keeps this Targeted.
- **Queue tooling that answers questions.** *Targeted.* `blamepost queue list` gives each waiting recipient with its attempt count, when it is next due, the exchanger it went to and what that exchanger said, narrowed by account or by receiving domain, and reports how close the spool is to its ceiling, because a list of waiting mail cannot on its own distinguish a queue that is filling from one that is merely busy. `blamepost queue held` answers the different question of what has stopped, counted by cause rather than listed per recipient, since one fault holds every message bound for the same place. `flush` retries and `remove` abandons one message with a recorded reason. Two things are missing. The spool keeps a full attempt history per recipient and a projection of how that recipient ends if nothing changes, and no surface reads either yet. And there is no operator hold, so a receiver an operator knows is down cannot be set aside and released later.

## Bounces, reports and notifications

- **Delivery status notifications.** *Targeted. Generation composed, interpretation not.* `b.mailBounce.dsn` and the bounce parser and handler beside it cover generation and interpretation, including vendor-specific shapes. Generation is composed and reaches the wire: a recipient that fails permanently produces a report, which is the entry below. Interpretation is the half nothing here reaches for, so a bounce arriving for an account is delivered to that account's mailbox as an ordinary message rather than being read and turned into a statement about the address it was about. RFC 3461, RFC 3464.
- **Putting a report on the wire.** *Shipped.* RFC 5321 §4.5.5 reserves the empty reverse path, and §6.1 requires it on every report a server generates, so a broken sender address cannot start a loop of reports about reports. Every report this server sends travels with it: the composer takes the empty string as the envelope sender and the transport writes `MAIL FROM:<>`, and a spool entry carrying the literal `<>` is read as the same value rather than handed to the address guard, which reads it as a malformed address. A report goes out over the same path as any other message, so it gets the same MX lookup, policy chain, spool and retry budget, and a report about a message that already arrived with the empty reverse path is suppressed rather than sent, which closes the loop the requirement exists for. Two bounds sit in front of generation, because a report is addressed to the sender of the message it is about, and on a run of mail to addresses that do not exist here that sender is whoever forged it: one bound per original sender, so a single forged address cannot be buried, and one across all of them, so a run spread over many forged addresses costs no more in total. Anything either bound refuses is recorded rather than dropped, as is a report the composer could not build at all, so an operator asking who was owed a report and did not get one finds every case under one set of actions.
- **Message disposition notifications.** *Accepted. Substrate shipped.* `b.mailMdn` builds and parses. Sending, parsing into the account's view and the allow-list decision are agent methods the framework leaves unimplemented, so they are blamepost's to build. A read receipt is a privacy decision as much as a feature, and the default is not to send one. RFC 8098.
- **Abuse reports.** *Accepted. Substrate shipped.* `b.mailArf` parses the feedback-loop format, which is how a receiver tells a sender that a recipient marked their mail as junk. Enrolling in feedback loops and acting on what arrives is operator workflow the admin surface should support. RFC 5965.
- **List unsubscribe.** *Accepted. Substrate shipped.* `b.mail.unsubscribe` builds the headers and handles the one-click endpoint. RFC 2369, RFC 8058.
- **Report ingestion in the interface.** *Accepted.* DMARC aggregate and failure reports and TLS-RPT reports parsed and surfaced in administration, rather than arriving as attachments nobody opens. Sending a domain's own aggregate reports as a receiver, too.

## Anti-abuse and content scanning

- **Blocklists.** *Targeted. Substrate shipped, not composed.* `b.mail.rbl` offers per-provider configuration and a documented posture, and the MX listener takes it as a gate. blamepost passes nothing to that gate and has no setting that would, so no deployment does blocklist lookups today. Wiring it means a configuration shape for which lists an operator trusts and what a hit does, which is the decision this item is really about.
- **Greylisting.** *Targeted. Substrate shipped, not composed.* `b.mail.greylist` offers a minimum delay and an allowlist time-to-live, keyed on a hashed fingerprint and a network prefix rather than a bare address. Same position as blocklists: the gate is accepted by the listener and nothing is passed to it. Greylisting also costs first-contact latency on legitimate mail, so it wants to be an operator decision rather than a default.
- **Rate limiting.** *Shipped.* `b.mail.server.rateLimit` is default-on inside every listener blamepost builds, covering concurrent connections per peer address, connection rate, an authentication-failure budget in a rolling window, and a recipient-failure budget on the MX listener. Every key here is the peer address, so a distributed attempt on one credential is not what these bound; the budget kept against the mailbox is the entry below. The byte-rate floor holds alongside them, on every listener that reads a transfer. A peer that trickles below a hundred bytes a second is cut: on both SMTP listeners and on both the `DATA` and `BDAT` paths, answered `421 4.7.0`; on IMAP, mid-literal, with `* BYE Literal arriving below the minimum rate`; and on ManageSieve for a `PUTSCRIPT` or `AUTHENTICATE` literal. The rate is judged over bounded windows rather than across the whole transfer, so an opening burst buys no credit against a slow tail, and each transfer is measured from its own start rather than inheriting the previous one's. The idle timeout answers a different question and still answers it: it ends a peer that has stopped sending, not one that has slowed down. Each mail listener also takes a ceiling of its own at a thousand and twenty-four concurrent sockets, so the process-wide total is bounded independently of the per-address cap, and a connection refused at that ceiling is recorded as `<listener>.max_connections_refused` carrying the peer address and the ceiling it hit, so a listener at capacity reads differently from an idle one. The floor's number is the framework's default and this server does not offer a setting for it; an operator sizing what a hostile peer can hold open sizes it against the two connection ceilings.
- **Per-identity authentication lockout.** *Shipped.* `b.auth.lockout` is composed in the identity layer every authenticating surface reaches, so the browser sign-in form and all five mail listeners spend one budget rather than six. It is keyed on the mailbox's canonical address, which is what bounds a credential-stuffing attempt spread across many source addresses: rotating addresses does not refill it, and neither does a plus tag on the local part. Five wrong credentials inside a quarter of an hour close the mailbox to further attempts, each subsequent lockout lasting longer than the one before it up to six hours, and an address with no account here spends the budget exactly as a real mailbox does so the refusal answers no question about which addresses exist. A source address the mailbox has already signed in from is still admitted while the budget is spent, so failing on somebody's behalf does not shut them out of their own mail, and each such address carries a second budget of its own, keyed on the mailbox and that source together and spent at the same five attempts a quarter of an hour. That one is read first, before the exemption is looked at, so an address the mailbox has signed in from before is still refused on its own count once it starts guessing. A successful sign in clears the budget for the address it came from and not the one kept against the mailbox, because a mail client authenticates on every poll and every send and would otherwise refill that budget for whoever is guessing; it decays a quarter of an hour after the last failure instead. Both budgets live in memory for the life of the process. Releasing one early is an operator action, and it lives on the administration console rather than on the command line for a reason worth stating: the budgets are counters inside the running server, and every `blamepost account` verb opens the data volume, which one process holds at a time, so a release issued with the server stopped would build an empty set of counters and report every time that nothing was locked. The console and the counters are in the same process. A release names the mailbox and a reason, may name one source address as well to release the smaller budget kept against that pair, and writes a row naming the operator who ran it.
- **Spam scoring.** *Targeted. Substrate shipped, not composed.* `b.mail.spamScore` scores in-process and `b.mail.scan` reaches an external scanner over the protocols the compose profile provides. Neither is wired into the delivery path yet, so the `scan` profile starts the services and nothing sends them a message.
- **Quarantine an account can review.** *Accepted.* Per-account thresholds, a training path from the junk folder, and a quarantine view. The project does not ship a classifier, because the corpus and the training are operator state, but the plumbing around one can be much better than it usually is.

## Accounts, domains and addressing

This is the layer the framework deliberately does not provide, and the first application code blamepost will carry.

- **Accounts.** *Targeted.* Credentials, status, quota policy and per-account settings, sealed at rest.
- **Domains.** *Targeted.* Hosted domains with their DKIM selectors, DNS posture acknowledgment and per-domain policy. Hosting several domains is a capability.
- **Aliases and forwarding.** *Targeted.* Address to account resolution, including catch-all and forwarding rules, with sender rewriting on the forward hop.
- **Address resolution at the wire.** *Targeted.* The lookup the MX and submission listeners call to decide whether an address is local and which mailbox it lands in.
- **Deletion posture.** *Targeted.* Deletion defaults to archive. Destroy requires an explicit flag and a recorded reason, and reaches the account row, the aliases pointing at it, and everything the account holds in its mailboxes: the messages, the filter scripts, the annotations and the sealed message bodies. It runs through the same delete path IMAP EXPUNGE takes, so a message under a preservation order or inside the retention floor stays and the command names it. GDPR Article 17 is the case this exists for. What it does not reach is a backup or a snapshot taken before it ran, since a message body is sealed under the volume's key rather than under anything the erasure destroys.
- **Per-domain key isolation.** *Accepted.* Making the isolation of keys, policy, quota and audit something an operator can reason about rather than something that happens to work.

## Composition and sending

The framework's agent implements read and mutate verbs and deliberately leaves the composition half unimplemented, listing them so an application knows exactly what it owns. That list is this section.

- **Compose, reply and forward.** *Targeted.* Building a standards-conformant message: header set, threading references that keep a conversation intact, quoting, attachment handling, and the multipart structure. RFC 5322, RFC 2045 through RFC 2049.
- **Send.** *Targeted.* Submitting a composed message through the delivery composer, appending to the sent folder, and reporting a failure to the person who pressed send rather than only to a log.
- **Identity management.** *Shipped.* The from-addresses an account may legitimately send as, checked against what the submission listener will accept, so the interface cannot offer an identity the wire will refuse. The browser and a JMAP client read the same set the submission port binds an author against, derived in one place rather than separately in three, so an address offered in a compose form is one the wire has already agreed to. One set answers both halves of the wire binding, so an address offered on a compose form is one `MAIL FROM` would take as well. These two surfaces still put the account's own address in the envelope and the chosen alias in `From` alone, so a bounce lands in the mailbox of whoever pressed send rather than in a shared address nobody reads. The set is read from the store on each request rather than held on the session, so an alias the operator withdraws stops being offered at the next message rather than at the next sign in. An alias is shown under its own name rather than the account holder's, because a departmental address may be held by several accounts at once and a message arriving under one holder's personal name tells the recipient something untrue about who sent it.
- **Import and export.** *Accepted.* Whole-mailbox movement in both directions, which is also the migration path below.

## Webmail

- **Reading.** *Targeted.* Folder list, message list, conversation view, and a message renderer that treats remote content and active content as hostile by default.
- **Search.** *Targeted.* All three surfaces answer a search, and not from the same substrate. JMAP `Email/query` and the browser read the store's full-text index. IMAP `SEARCH` scans the rows instead, because RFC 9051 §6.4.4 makes every string key a substring match while the index matches whole tokens, folds the sender and the recipients into one column and drops stopwords: reading it would hand a client a tagged `OK` with messages missing from the set, which is indistinguishable from a mailbox that does not hold them. So the flags, keywords, sizes, arrival dates, sequence sets and the `SUBJECT`, `FROM`, `TO` and `HEADER` keys are answered from the fields the store keeps whole. The keys it cannot answer honestly are refused at the point of parse rather than evaluated in part: `CC`, `BCC`, `BODY`, `TEXT` and the `SENT` dates all ask about headers or body parts that are not kept whole, and an expression has no partial evaluation, so answering `OR SUBJECT round CC bravo` from the half that runs would report the messages matching a query the client never sent. Each refusal names the key and says what is answered instead. Keeping the fields those keys ask about, so that one substrate answers all three surfaces the same way, is what keeps this Targeted. RFC 9051 §6.4.4.
- **Composing.** *Targeted.* Compose, reply, reply-all, forward, drafts, and attachments.
- **Organizing.** *Targeted.* Move, flag, mark, delete, folder management, and the Sieve rule surface.
- **Server-rendered first.** *Targeted.* The interface renders on the server, with client JavaScript as opt-in islands rather than a required runtime. The backend validates and the frontend displays, with no duplicate validation shipped to the browser.
- **Accessibility and small screens.** *Accepted.* A mail client people read on a phone. Treated as a requirement rather than a later pass.

## Administration

- **Domains, accounts and aliases.** *Targeted.* The management surface for the identity layer.
- **DKIM selector lifecycle.** *Targeted.* Generation, publication and rotation, with the retiring selector left published long enough to cover in-flight mail rather than pulled immediately.
- **Queue inspection.** *Targeted.* What is waiting, why, and what to do about it.
- **Audit.** *Targeted. Substrate shipped and composed.* `b.audit` provides a namespaced, tamper-evident record, and every administrative change to an account, a domain or an alias writes a chained row naming what was done, how it came out, which record it touched and who was responsible. The acting identity is carried rather than threaded by hand: the command line runs every verb under the operator who invoked it, and the browser surface opens the same scope on every request before a route runs, so a row written deep in the identity layer names the person without each verb having to pass them down. A request carrying no session still opens one, because where a refusal came from is most of what a refusal is read for. Two rows deliberately name somebody other than an operator: an account proving its own credential names that account, and a refused attempt names only the peer, since at that moment the address is a claim and the peer is a fact. `blamepost domain acknowledge` records both of the facts it holds, the operator who ran the verb in the actor field and the name they vouched for beside it, because folding either into the other leaves the trail unable to answer the question the other one holds. The DKIM selector lifecycle records minting, rotation and retirement, and a rotation names both selectors rather than only the one that arrived, since an auditor reading a key change asks what it replaced. A trail that cannot be written does not cost the change it describes: the row is written after the change has reached disk, so an unavailable sink drops the row and the verb still reports its own outcome, rather than a bookkeeping failure being read as the operation having failed. A change originating inside the framework's own mail agent carries its actor into the chain in the identifier the chain writer reads, with the address, user agent and session alongside it. What keeps this Targeted is that no vector here drives a framework-agent row end to end, so the guarantee is one this server inherits rather than one it measures.
- **DNS posture check.** *Targeted.* `blamepost doctor` resolves the live posture, compares it against what the server expects, and names precisely which record is wrong. It covers MX, SPF, DMARC, DKIM, MTA-STS as both the TXT record and the fetched policy, TLS-RPT, and TLSA under `--dane`, alongside the local checks for the certificate, the data directory and the two halves of the acknowledgment. Every lookup it makes is bounded, so a resolver that accepts a question and never answers cannot hold the run open, and a record it could not get an answer about is reported as a third kind of result rather than as a missing one: unchecked names neither what was expected nor what was found, because neither was seen, and it sends the operator to the resolver rather than to the zone. A run that could not settle every question does not report itself as passing. Three gaps keep it Targeted: it does not count the DNS lookups an SPF evaluation would spend against the limit of ten, it resolves no `PTR` for this server's own sending address, and it has no memory of a previous MTA-STS `id`, so it cannot see one that was not bumped when the policy changed. The boot gate refuses to serve mail until the operator confirms the posture, and this is the tool that makes that confirmable rather than a guess.
- **Publishing DNS records from the server.** *Targeted. The DMARC record ships; the rest are published by hand.* `BLAMEPOST_ZONE_PROVIDER` names a hosted DNS provider and `blamepost zone token set` seals a credential for it onto the data volume; `blamepost zone preview` and `blamepost zone verify` then hold a zone up against the DKIM selector records this server expects, reading it from the provider and through a resolver and separating a record that has not propagated from one that resolves to something else. The DMARC page in the administration console publishes the `_dmarc` record for one hosted domain: it shows the change set publishing a level would make, holds that set in the running server, and performs the set the operator confirmed against rather than one recomputed at the moment of the write. The write gate refuses everything it should: a fixed set of addresses under one hosted domain, a preview that has to still be true when it is performed, a ceiling on the changes one set may carry, a reason on every write, and `MX` behind a switch of its own that is off, because repointing `MX` moves delivery away from the process that would have reported it. A record is removed only where the change set already names that type at that address, so an address the set says nothing about is left standing, and any removal at all is performed only once the operator confirms it against the diff. After a write each record is read back at the provider and again through a resolver, so a write the provider accepted and a resolver cannot find is reported rather than missed, and a resolver answering with something else is reported apart from one that has not answered yet. A stored token that is not sealed is refused rather than opened. What keeps this Targeted is the rest of the write set. The sender policy, the MTA-STS pair, the TLS reporting address and the DANE associations are composed in the gate and reachable from no operator surface, so those records are still published by hand from what `blamepost doctor` and `blamepost dkim records` print. The DKIM selector records are the next of them, because this server holds the only authoritative value for those and they change on a schedule.
- **Deliverability diagnostics.** *Accepted.* Forward-confirmed reverse DNS, blocklist lookups against the sending address, a warm-up-aware view of outbound volume, and a plain statement of what a receiver is likely to make of this server today.
- **Client autoconfiguration.** *Accepted. Substrate shipped.* `b.mail.deploy.autoConfigXml` and `.autoDiscoverXml` emit the documents that let a client ask for its settings instead of the operator writing them down.

## Storage, backup and retention

- **Mail store.** *Shipped as substrate.* `b.mailStore` is the byte-level substrate: append with parse and threading, fetch, search, flags, folders, quota, move and hard expunge, over SQLite by default. Subject, sender, recipients and bodies are sealed at rest, so a database dump yields no recoverable message content, while the fields needed for forensics stay queryable in the clear.
- **Legal hold.** *Shipped.* Hard deletion routes through one path, and a message under hold survives it: the client is not told the message went, a later session still finds it, and the body is still readable. IMAP expunge, POP3 delete and JMAP destroy all reach that path, and a wire handler that deletes directly is a defect. A hold is set through the store rather than over the wire, because no mail protocol has a verb for it.
- **Retention floor.** *Shipped, off by default.* `BLAMEPOST_COMPLIANCE_POSTURE=soc2` sets a one year floor below which a hard delete is refused, for the account owner as much as for an administrator. With no posture set the floor is zero and a legal hold is the only thing that keeps a message, which is the default and is what most operators want.
- **The three postures blamepost does not offer.** *Under design.* The framework also models `hipaa`, `pci-dss` and `gdpr`, and under each of those the mailbox agent refuses every operation whose actor does not carry a field naming why that particular access is lawful: `purposeOfUse`, `pciScope`, `lawfulBasis`. Those are judgments about an access rather than properties of a server, and blamepost has no model that could supply one. The guard checks only that the field is a non-empty string, so a hardcoded value would satisfy it, which is the reason not to write one: it would manufacture an attestation nobody made and pass the control while defeating it. Configuration refuses those three at boot rather than letting a server start and answer NO to every mailbox call. Offering them means giving accounts and sessions a purpose-of-access model first.
- **Backup and restore.** *Targeted.* A documented, exercised path for the data volume, with the restore verified rather than assumed. A backup nobody has restored is a hypothesis.
- **Migration in.** *Accepted.* Import over IMAP from an existing server, and from Maildir and mbox on disk, with progress, resumption and a report of what did not survive. Migrating onto a mail server is where most self-hosting attempts stop, so this is a first-class feature rather than a script in the documentation.
- **Storage format stability.** *Accepted.* Frozen for 1.0, with a migration for every change that reaches an existing volume.

## Transport security and certificates

- **Operator-supplied certificates.** *Targeted.* `BLAMEPOST_TLS_CERT` and `BLAMEPOST_TLS_KEY` name the pair every listener presents, and `serve` refuses to start without them. The key may be sealed with the vault passphrase, in which case it is unsealed in memory and never written back in the clear. This is the only way blamepost gets a certificate: from an ACME client you already run, from an internal authority, or from the pair a terminator in front already holds.
- **Listener TLS.** *Targeted. Substrate shipped.* `b.mail.server.tls` loads that pair and watches it, so a renewal written to the same paths is picked up in process rather than at the next restart, and the context it builds advertises RFC 8879 certificate compression. Every listener presents one key-agreement preference, the ML-KEM hybrids ahead of every elliptic curve RFC 8446 §4.2.7 registers, which is an order rather than a set: a peer naming a hybrid anywhere in its offer is retried onto the hybrid instead of being served the classical curve it happened to put first. The browser interface carries the same preference by a different route, since it builds its TLS port from the certificate bytes rather than sharing the mail listeners' context. What keeps this Targeted is that a hybrid can only be reached with a peer that implements one, and nothing records which group ran: the call naming a negotiated group answers on a client socket and returns nothing on a server one, so an operator cannot measure how much inbound mail arrived over a classical exchange. Closing that needs the runtime to answer on the accepting end.
- **Certificate provisioning.** *Accepted. Substrate shipped.* `b.acme` covers issuance and renewal, including the renewal-information extension that lets a certificate authority signal an early renewal (RFC 8555, RFC 9773). What is missing is the half the framework leaves to the application: answering the HTTP-01 or DNS-01 challenge, which needs either port 80 in the listener set or a resolver credential this server does not hold. Until that is settled, blamepost orders no certificates and renews none, and no configuration setting claims otherwise.

## Message-level cryptography

- **PGP and S/MIME.** *Accepted. Substrate shipped.* `b.mail.crypto.pgp` and `b.mail.crypto.smime` exist in the framework. What blamepost owns is the key-handling and interface questions, which are the hard part: where a private key lives, whether the server ever holds one, and how a verification result is shown without implying more than it means.

## Calendars and contacts

- **CalDAV and CardDAV.** *Under design. Substrate shipped.* `b.mail.dav` exists. Whether this ships depends on whether operators want it in the same process or would rather run it separately, and that question is worth asking before building.

## Observability

- **Structured logging.** *Targeted. Substrate shipped.* `b.log` with request correlation.
- **Health and readiness.** *Targeted.* Readiness reports listener and store state rather than process liveness, so a container that booted but failed to bind is unhealthy instead of quietly accepting nothing.
- **Metrics.** *Accepted.* Counters and histograms for the paths an operator actually watches: accept and reject rates by reason, queue depth and age, delivery outcome by destination, authentication failures.
- **No telemetry.** *Shipped as policy.* Nothing phones home. No upstream exists to report to, and no instance to join.

## Deployment and packaging

- **Container image.** *Shipped as definition, targeted as a published artifact.* The build, scan, sign and publish pipeline is in place; the first published image ships with the first release that has a server in it.
- **Registry publication.** *Targeted.* Published to npm as `@blamejs/blamepost` with provenance, and to the container registry, from the same tagged release.
- **Compose stack.** *Shipped.* The single image is the documented default. Optional content-scanning and reverse-proxy services sit behind profiles and are off unless asked for.
- **Reproducibility.** *Accepted.* A build that produces identical bytes from identical inputs, which is what makes the provenance attestation worth checking.

## Assurance and interoperability

- **Layered test suite.** *Targeted.* Primitives and static gates, then state-bearing tests, then wire-protocol integration against real clients and servers.
- **Parser hardening.** *Accepted.* The wire readers face attacker-supplied bytes daily. Fuzzing, adversarial fixtures, and a structural detector for any class a bug turns out to belong to, so the same shape cannot return quietly.
- **Independent validation.** *Accepted.* An implementation this project did not write should exercise every protocol it speaks. Where that is possible it becomes part of the suite rather than a manual check.
- **Coverage as a bug-hunt vehicle.** *Accepted.* Branch coverage over the application layer, with an explicit account of swallowed error paths.

## Continuous, not a milestone

These run every release rather than arriving in one. Post-quantum posture tracked against the NIST and IETF surface, adopting platform implementations only where they reach byte parity with the vendored ones and never rolling forward silently. Vendored-framework currency checked against the registry on every pull request, so a stale pin fails the release. Supply-chain assurance across signed tags, provenance, signed SBOMs, digest-pinned actions and base images, and integrity verification of the vendored tree. Node LTS tracking as the engine floor rises.

## Deliberately excluded

- **A hosted service.** blamepost is software an operator runs on their own machine for their own domains. The project ships no instance to join, no upstream to phone, and no telemetry, and has no interest in becoming a service.
- **npm runtime dependencies.** One vendored framework, pinned to a published version and integrity-verified, and nothing else.
- **A build step.** No TypeScript and no transpilation. The source in the repository is what the runtime executes, because every transpilation step is a supply-chain hop.
- **Classical-only cryptographic defaults.** Classical algorithms appear where a wire format requires them, beside a post-quantum choice, never instead of one.
- **Security defaults behind flags.** They are part of the boot sequence, not configuration.
- **Tolerant parsers.** Input the standard forbids gets refused, whatever client sent it.
- **Silent breaking changes in a minor.** The upgrade policy is a constraint, not an aspiration.

## Influencing it

Open an issue or a discussion. A change affecting DNS, data at rest, or a wire-visible default goes through the proposal process in [GOVERNANCE.md](GOVERNANCE.md). Security-sensitive direction is best raised privately first, per [SECURITY.md](SECURITY.md).

The most useful contribution an operator can make is a report from a real deployment: which client disagreed, which receiver refused, which record was wrong. That is what moves the order of this list.
